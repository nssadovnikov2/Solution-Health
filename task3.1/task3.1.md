## Задание 3. Проектирование ключевых архитектурных решений для интеграции ИТ-систем
### 3.1. Надёжная поставка результатов анализов в мобильное приложение
Текстовое описание решения
Проблема: В текущей архитектуре передача результатов анализов из LIS в CRM происходит через ненадёжный REST-коннектор на Perl с FTP-загрузкой. Данные теряются, задерживаются до 2 часов, дублируются (INT-002, INT-008, INT-011). Пациенты не видят анализы в онлайн-режиме.

Решение: Внедрение событийно-ориентированной архитектуры (EDA) с гарантированной доставкой через брокер сообщений (Kafka).

Как это работает:

LIS публикует событие LabResultsReady в топик Kafka сразу после завершения автоматической загрузки данных с оборудования (через FTP). В событии содержится ID пациента, ID заказа на анализы, ссылка на файл с результатами (или сам JSON с результатами).

Сервис-агрегатор (новый компонент) потребляет событие, обогащает его (добавляет контактные данные пациента из CRM), сохраняет результат в Read Model (отдельная таблица в PostgreSQL для быстрого чтения мобильным приложением) и отправляет событие NotificationRequested в Kafka для триггера пуша.

Сервис уведомлений получает событие и отправляет пациенту пуш: «Ваши анализы готовы».

Мобильное приложение через API Gateway запрашивает результаты анализов из Read Model, а не из CRM напрямую.

Ключевые паттерны:

Transactional Outbox (на уровне LIS): Событие сохраняется в локальной таблице LIS в одной транзакции с данными, затем отдельный процесс публикует его в Kafka. Гарантирует, что событие не потеряется, даже если LIS упала после сохранения данных.

Event Sourcing (частичный): Храним все события по анализам в Kafka с retention 30 дней. Позволяет перечитать историю и восстановить состояние при сбоях.

CQRS (Read Model): Отдельная модель данных для чтения мобильным приложением, обновляемая асинхронно из событий. Разгружает операционную CRM и LIS.

Обработка ошибок:

При сбое consumer’а (например, CRM недоступна) — автоматический retry с exponential backoff (3 попытки, задержка 1, 5, 15 секунд).

При критической ошибке — сообщение уходит в DLQ (Dead Letter Queue) для ручного разбора.
