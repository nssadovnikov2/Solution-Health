### 3.1. Надёжная поставка результатов анализов в мобильное приложение

#### Текстовое описание решения

**Проблема:** В текущей архитектуре передача результатов анализов из LIS в CRM происходит через ненадёжный REST-коннектор на Perl с FTP-загрузкой. Данные теряются, задерживаются до 2 часов, дублируются (INT-002, INT-008, INT-011). Пациенты не видят анализы в онлайн-режиме.

**Решение:** Внедрение событийно-ориентированной архитектуры (EDA) с гарантированной доставкой через брокер сообщений (Kafka).

**Как это работает:**

1. **LIS публикует событие** `LabResultsReady` в топик Kafka сразу после завершения автоматической загрузки данных с оборудования (через FTP). В событии содержится ID пациента, ID заказа на анализы, ссылка на файл с результатами (или сам JSON с результатами).

2. **Сервис-агрегатор (новый компонент)** потребляет событие, обогащает его (добавляет контактные данные пациента из CRM), **сохраняет результат в Read Model** (отдельная таблица в PostgreSQL для быстрого чтения мобильным приложением) **и отправляет событие** `NotificationRequested` **в Kafka для триггера пуша**.

3. **Сервис уведомлений** получает событие и отправляет пациенту пуш: «Ваши анализы готовы».

4. **Мобильное приложение** через API Gateway запрашивает результаты анализов из Read Model, а не из CRM напрямую.

---

**🔄 ИСПРАВЛЕНИЕ 1: Устранение Dual Write в Сервисе-Агрегаторе**

> **Проблема:** В исходном решении Сервис-Агрегатор выполнял две операции последовательно: сначала сохранял данные в Read Model, затем публиковал событие в Kafka. При сбое между этими шагами (Read Model обновлена, а Kafka недоступна) пациент не получал бы пуш, хотя анализы уже готовы. Это классический антипаттерн **«Двойная запись» (Dual Write)**.
>
> **Исправление:** В Сервисе-Агрегаторе внедряем **Transactional Outbox**.
>
> 1. В рамках **одной транзакции PostgreSQL** сервис одновременно:
>    - Сохраняет обогащённые данные в таблицу `read_model`.
>    - Записывает событие `NotificationRequested` в таблицу `aggregator_outbox` со статусом `PENDING`.
>    
>    Это гарантирует атомарность: либо обе операции выполняются, либо ни одна не фиксируется.
>
> 2. Отдельный фоновый процесс (Poller) периодически опрашивает таблицу `aggregator_outbox`, публикует события в Kafka и меняет статус на `SENT`.
>
> 3. Если публикация в Kafka временно недоступна, событие остаётся в таблице и будет отправлено при восстановлении соединения (гарантированная доставка).

---

**🔄 ИСПРАВЛЕНИЕ 2: Идемпотентная обработка на входе в Сервис-Агрегатор**

> **Проблема:** При повторном чтении одного и того же события из Kafka (например, после сбоя consumer’а или при replay) Сервис-Агрегатор мог обработать его повторно, создав дублирующие записи в Read Model и отправив дублирующиеся уведомления.
>
> **Исправление:** Добавляем **идемпотентность по `result_id`**.
>
> 1. Каждое событие `LabResultsReady` содержит уникальный идентификатор результата анализов (`result_id`).
> 2. Перед обработкой события Consumer проверяет наличие этого `result_id` в таблице `read_model`.
> 3. Если запись уже существует — событие **игнорируется** (отправляется ACK без обработки).
> 4. Если записи нет — выполняется полный цикл обработки (обогащение → сохранение в Read Model → запись в Outbox).

---

**Ключевые паттерны:**

| Паттерн | Где применяется | Назначение |
| :--- | :--- | :--- |
| **Transactional Outbox** | LIS и Сервис-Агрегатор | Гарантирует атомарность между сохранением данных и публикацией событий. Исключает потерю событий при сбоях. |
| **Идемпотентность** | Сервис-Агрегатор (по `result_id`) | Предотвращает дублирование записей и уведомлений при повторной обработке событий из Kafka. |
| **Event Sourcing (частичный)** | Kafka (retention 30 дней) | Храним все события по анализам, что позволяет перечитать историю и восстановить состояние при сбоях. |
| **CQRS (Read Model)** | Read Model PostgreSQL | Отдельная модель данных для чтения мобильным приложением, обновляемая асинхронно из событий. Разгружает операционную CRM и LIS. |

**Обработка ошибок:**

- При сбое consumer’а (например, CRM недоступна) — автоматический retry с exponential backoff (3 попытки, задержка 1, 5, 15 секунд).
- При критической ошибке — сообщение уходит в DLQ (Dead Letter Queue) для ручного разбора.
- При сбое публикации из Outbox в Kafka — Poller продолжает попытки до успеха; событие не теряется.
