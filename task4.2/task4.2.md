### Таблица стратегий горизонтального масштабирования для критичных систем

| ИТ-система | Реализация горизонтального масштабирования | Ключевое ограничение | Решение ограничения |
| :--- | :--- | :--- | :--- |
| **Сервис Расписания (микросервис)** | **Stateless-развёртывание:** Несколько экземпляров сервиса (подов) в Kubernetes. Балансировщик распределяет трафик. Состояние (база данных) вынесено в PostgreSQL (stateful). | **PostgreSQL блокировки при записи** (INT-009). При высоком RPS запись в одну таблицу создаёт блокировки строк, что ограничивает пропускную способность. | **CQRS + Read Replica:** Запись идёт в мастер PostgreSQL, чтение (просмотр слотов, аналитика) идёт через Read Replica. Для записи внедряем **партиционирование таблицы слотов по `clinic_id`**, чтобы снизить конкуренцию. |
| **Сервис Уведомлений** | **Горизонтальное масштабирование consumer'ов:** Увеличиваем число партиций в RabbitMQ/Kafka и запускаем несколько экземпляров consumer'ов (Competing Consumers). Каждый экземпляр обрабатывает свою часть очереди. | **RabbitMQ — единая точка отказа** и ограничение по throughput (как указано в INT-004, очередь переполняется при пиках). | **Переход с RabbitMQ на Kafka:** Kafka обеспечивает лучшее масштабирование за счёт партиционирования. Увеличиваем число партиций топика `notification-events` до 10, чтобы 10 consumer'ов могли обрабатывать пуши параллельно. Внедряем мониторинг **consumer lag**, чтобы автоматически добавлять новые поды при отставании. |
